# Development guide

## Principles

1. Integrate mature providers when their APIs, permissions, quotas, and terms fit.
2. Build the unified project/campaign/task/wallet/points/earnings experience ourselves.
3. Treat provider data as sourced and time-stamped; distinguish verified facts from estimates.
4. Keep the first release small and inexpensive. Prefer free tiers and cache responsibly.
5. Never store wallet secrets or execute transactions on behalf of the user.
6. Preserve the existing Android UI and user-visible flows during architecture work.

## Database migration rules

- Every schema change after the bootstrap revision must be a new file under `backend/app/migrations/versions/`.
- Never edit a revision that has already been applied to a shared or production database.
- Review generated migrations before applying them; autogenerated output is a draft, not an approval.
- Take and verify a database backup before production schema changes.
- Keep migrations additive and data-preserving where possible. Destructive changes require an explicit data migration and rollback plan.
- The bootstrap revision adopts the existing Render schema without dropping tables or records.

## Production readiness checklist

- Verify authentication, authorization, and user-level isolation for every account-specific endpoint.
- Verify PostgreSQL backups, restore procedures, migration history, and deployment rollback.
- Add provider adapters only after checking official API documentation and terms.
- Add rate limits, retries with backoff, caching, observability, and sync-run history.
- Review external URLs, contract/address inputs, imported content, and WebView navigation boundaries.
- Configure secrets in the deployment environment, never in source control.
- Do not describe mock/local-only synchronization as cloud synchronization.
